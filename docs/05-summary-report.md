## 1. 项目背景与小组分工

### 项目背景
本实验以“校园活动报名与签到管理系统”为统一项目背景。该系统旨在支持活动发布、学生报名、名单审核、二维码签到、签到统计和活动总结导出等基本功能。本次实验聚焦软件项目管理过程，通过 Git 版本管理工具完成项目初始化、三级 WBS 分解、进度计划编制、配置管理、分支协作、冲突解决及总结报告提交，重点训练项目管理成果的形成、版本受控和协作留痕能力，不要求实现完整的业务系统。

### 项目目标
- 建立统一的项目仓库与目录结构
- 完成围绕交付物的三级 WBS 分解
- 制定简化进度计划（含活动、工期、前置关系、责任人）
- 制定配置管理方案（配置项识别、分支策略、提交与合并规则）
- 制造并解决一次 Git 冲突，记录解决过程
- 全体成员共同完成总结报告，并提交至 main 分支

## 2. WBS 分解思路

本项目的 WBS 遵循 **结果导向** 原则，每个节点均代表一个可交付的成果或文档，避免使用“开会、讨论、写代码”等过程性动作。

### 一级交付物（4个）
- **A. 版本管理基础成果**：确保团队在开始文档编写前拥有统一的协作基础设施（仓库、目录、首次提交）。
- **B. 项目管理文档成果**：实验考核的核心文档，按文档类型拆分便于分配责任人和并行工作。
- **C. 协作实践成果**：覆盖冲突制造、分支合并等 Git 协作技能，是实验的难点和亮点。
- **D. 总结报告成果**：整合全过程，体现团队反思和最终输出。

### 二级与三级分解示例（以 B. 项目管理文档成果为例）
- **B.1 项目启动文档**
  - B.1.1 编写项目背景与目标
  - B.1.2 编写团队成员与角色分工表
  - B.1.3 编写项目边界（纳入/不纳入范围）
  - B.1.4 列出主要交付物清单
- **B.2 WBS 文档（本文件）**
  - B.2.1 识别主要交付物
  - B.2.2 按结果导向分解到三级
  - B.2.3 编写分解思路说明
- **B.3 简化进度计划文档**
  - B.3.1 从 WBS 中提取关键活动
  - B.3.2 填写工期、前置关系与责任人
  - B.3.3 生成 Markdown 格式进度计划表
- **B.4 配置管理文档**
  - B.4.1 识别配置项（README, docs/*.md 等）
  - B.4.2 制定分支策略（main / feature/*）
  - B.4.3 编写提交规范与合并规则
  - B.4.4 编写版本标记方法（tag）

### 分解说明
- 一级交付物划分为四类，覆盖实验要求的全部交付范围，边界清晰。
- 二级分解按照逻辑阶段或文档类型划分。
- 三级分解到可独立分配、可验证的最小成果单元。

## 4. 配置管理与协作过程

### 配置项识别
根据实验要求，本项目的配置项包括：
- `README.md`：项目说明与协作约定
- `01-project-charter.md`：项目启动说明
- `02-wbs.md`：三级 WBS 分解文档
- `03-schedule.md`：简化进度计划
- `04-config-plan.md`：配置管理方案
- `conflict.md`：冲突示例文件
- `conflict-resolution-log.md`：冲突解决日志
- `05-summary-report.md`：总结报告
- 目录结构（docs/, src/, test/, assets/）

### 分支策略
- **main**：主分支，存放最终稳定版本，禁止直接提交。所有修改必须通过 feature 分支合并。
- **dev**：开发汇总分支（本实验未强制使用，但策略中保留）。
- **feature-***：功能分支，用于单独开发文档与目录。命名格式如 `feature/wbs`、`feature/schedule`、`feature/summary-report`。

### 命名约定
- **文档命名**：使用 `01-xxx.md` 数字序号格式，清晰统一。
- **分支命名**：功能分支以 `feature-模块名` 或 `feature/模块名` 格式命名。
- **提交说明**：采用 `类型: 描述内容` 格式，例如：
  - `docs:` 文档修改
  - `feat:` 新增目录/文件
  - `fix:` 修复错误、解决冲突
  - `merge:` 合并分支

### 合并规则
- **合并负责人**：项目经理（成员A）。
- **合并时机**：单个任务完成 → 合并到 main；或先合并到 dev 再合并到 main（本实验实际操作中 feature 分支直接合并到 main）。
- **冲突处理流程**：
  1. 先拉取最新版本
  2. 手动删除冲突标记，保留正确内容
  3. 提交解决后的文件
  4. 完成合并并推送

### 版本留痕
- 每个任务完成后必须提交，保留阶段性记录。
- 所有提交使用规范说明，便于追溯修改人、修改时间、修改内容。
- 不删除任何分支，保留完整开发历史。
- 全部内容同步到 GitHub 远程仓库，永久留痕。

### 实际协作过程
本实验严格按照上述配置管理方案执行。所有文档均通过 feature 分支开发，完成后由项目经理合并到 main。冲突制造与解决环节遵循了合并规则，成功解决了 `conflict.md` 中的冲突，并记录了解决日志。目前所有文档均已受控，最终总结报告完成后将合并到 main 并打标签 `v1.0-final`。

## 5. 冲突解决过程记录

### 冲突基本信息
- **冲突文件**：`docs/conflict.md`
- **涉及成员**：成员A（zhaojiameizhi）与成员D（ganquan）
- **冲突类型**：同一行代码修改冲突 + 文件结构冲突
- **解决时间**：2026-05-01

### 冲突制造步骤
1. 成员A在分支 `feature/conflict-edit` 中将 `conflict.md` 中的“当前结论”行修改为：“本组决定先经过 dev 再合并到 main”。
2. 成员D在分支 `feature/conflict-ganquan` 中将同一行修改为：“本组决定直接合并到 main”。
3. 两个分支分别提交并推送到远程。

### 冲突发现与解决过程
当项目经理尝试将两个分支合并到 main 时，Git 检测到同一行内容被不同方式修改，触发了合并冲突。

**解决方式**：
1. 团队成员通过在线沟通协商，最终决定采用成员A的版本（先合并到 dev 再合并到 main），因为该方案更符合实验要求的分支策略。
2. 手工编辑 `conflict.md`，删除冲突标记，保留选定内容。
3. 同时恢复被误删的「建议操作」模块，确保文件结构完整。
4. 提交解决后的文件并完成合并。

### 最终结果
- 冲突已完全解决，`conflict.md` 内容正确，文件结构完整。
- 解决过程记录在 `conflict-resolution-log.md` 中。
- 合并后的 main 分支包含正确的冲突解决版本。

### 经验总结
本次冲突实践让团队深刻理解了 Git 的冲突标记和手工解决机制。成功的关键在于及时沟通、明确规则以及详细的日志记录。
